# outline-first-writing

## Overview

适用于**大体量产出**：长文档、超大代码文件、多文件批量实现。核心原则统一为：**先结构，后展开**。

- 文档场景：**大纲即契约**——未经确认的大纲不得进入正文撰写。
- 代码场景：**骨架即契约**——未经确认或未校验的文件骨架，不得直接一次性灌入完整实现。

## 触发条件

满足任一即触发：
- 文档预估产出 **> 500 行**
- 文档包含 **3 个以上章节**
- 单个代码文件预估 **> 200-300 行**
- 需要一次新增/重写 **多个新文件**
- 用户明确要求“先出大纲 / 先搭骨架 / 分段来”
- 大文件写入工具（如 Write）连续失败，需切换到分段 patch / 分块编辑

不触发：
- 单章短文、README、changelog、代码注释等小型写作
- 单文件小改动
- 单点函数补丁

## SOP 流程（总则）

先判断产出类型：

- **A. 文档型** → 走“大纲分支”
- **B. 代码型** → 走“骨架分支”

二者共享总流程：

```
判断是否触发?
 ├─ 不触发 → 正常流程（结束）
 └─ 触发 ↓

识别产出类型?
 ├─ 文档 → P1 先大纲
 └─ 代码 → P1 先骨架
         ↓
P2 评审/确认 ──需调整──→ 回到 P1
 │
 通过 ↓
P3 分段展开
 ↓
P4 分段验证 ──修正──→ 回到 P3
 │
 通过 ↓
P5 交付收尾（结束）
```

| 阶段 | 文档型 | 代码型 | 门禁 |
|------|--------|--------|------|
| P1 | 拟大纲（读者/命题/体量 + 每章摘要） | 拟骨架（文件树/模块职责/分块顺序） | — |
| P2 | 用户确认大纲；可选 `@oracle` 评审 | 用户确认骨架（或任务明确时直接进入） | **未确认前禁止写正文/实现** |
| P3 | 按大纲逐章撰写 | 按骨架分块写入，每块可独立验证 | 结构变更须获用户确认 |
| P4 | 正文评审（用户 / `@oracle`） | 每块最小验证（语法/smoke/测试） | 未通过则回 P3 |
| P5 | 更新元数据、文档导航 | 汇总文件清单、验证结果、风险点 | — |

## A. 文档分支（保留原流程）

```
判断是否触发?
 ├─ 不触发 → 正常写作流程（结束）
 └─ 触发 ↓

P1 拟大纲
 ↓
P2 大纲评审 ──修改──→ 回到 P1
 │
 确认 ↓
P3 逐章撰写
 ↓
P4 正文评审 ──修改──→ 回到 P3
 │
 通过 ↓
P5 交付收尾（结束）
```

| 阶段 | 名称 | 关键动作 | 门禁 |
|------|------|----------|------|
| P1 | 拟大纲 | 明确读者/命题/体量，产出含每章摘要的大纲 | — |
| P2 | 大纲评审 | 用户确认大纲；可选 `@oracle` 专家评审 | **用户未确认前禁止写正文** |
| P3 | 逐章撰写 | 按大纲顺序逐章写，todowrite 标记进度 | 结构变更须获用户确认 |
| P4 | 正文评审 | 用户 / `@oracle` 评审，逐条修订 | 评审未通过则回 P3 |
| P5 | 交付收尾 | 更新元数据、文档导航，报告交付物 | — |

### 阶段 1：拟大纲

1. 明确文档**目标读者**、**核心命题**、**预期体量**。
2. 产出大纲，每章包含：
   - 章节编号与标题
   - 1-2 句内容摘要（写什么、为什么需要这章）
   - 预估行数（可粗略）
3. 大纲末尾附"附录/补充材料"占位（如有）。

**大纲模板：**

```markdown
# 《文档标题》大纲

- **目标读者**：xxx
- **核心命题**：xxx
- **预估体量**：约 xxx 行，N 章 + M 个附录

## 章节结构

### 第1章 xxx
内容摘要：xxx（约 xx 行）

### 第2章 xxx
内容摘要：xxx（约 xx 行）

...

### 附录
- 附录A：xxx
- 附录B：xxx
```

### 阶段 2：大纲评审

- 将大纲呈现给用户，明确询问：**"大纲是否可以？需要调整哪些章节？"**
- 若用户要求修改 → 回到阶段 1 修订。
- 若用户确认 → 进入阶段 3。
- **（可选）** 调度 `@oracle` 对大纲做专家评审，与用户评审并行或串行均可。

**硬门禁：用户未确认大纲前，禁止撰写任何正文。**

### 阶段 3：逐章撰写

1. 按大纲顺序逐章撰写。
2. 每章完成后用 `todowrite` 标记进度。
3. 若写作过程中发现需要调整大纲结构（新增/删除/合并章节），必须先向用户说明变更理由并获得确认，再继续。

### 阶段 4：正文评审

- 全文完成后，进行评审（用户评审 和/或 `@oracle` 专家评审）。
- 评审产出改进建议 → 逐条修订 → 复核。
- 评审通过 → 进入阶段 5。

### 阶段 5：交付收尾

1. 更新文档元数据（版本号、状态、日期）。
2. 更新 `docs/文档导航.md`（如文档存放在 `docs/` 下）。
3. 向用户报告交付物路径与版本。

## B. 代码分支（新增）

### 阶段 1：先骨架

在真正写大代码前，先产出“实现骨架”，至少包含：

1. **文件树 / 变更清单**：要新增/修改哪些文件。
2. **每个文件职责**：每个文件做什么。
3. **函数/模块清单**：核心函数、入口、依赖关系。
4. **分块顺序**：先写哪块，再写哪块。
5. **验证计划**：每块写完如何验证（如 `bash -n`、最小 smoke test、局部测试）。

**代码骨架模板：**

```markdown
# 《任务名》实现骨架

## 文件结构
- file A：入口 / 路由
- file B：公共函数
- file C：domain 实现

## 模块职责
- A：负责参数分发
- B：负责公共能力
- C：负责业务动作

## 分段顺序
1. 先写入口骨架
2. 再写公共库
3. 再按 domain 分块补实现
4. 每块完成即做最小验证

## 验证计划
- 语法检查：xxx
- smoke test：xxx
```

### 阶段 2：骨架评审/确认

- 若用户明确要求先确认，则先等用户确认。
- 若用户未要求显式确认，但任务已明确，可按骨架直接进入实现。
- 若中途发现骨架要大改（新增文件、职责重排、拆分方式变化），先说明再继续。

### 阶段 3：分段展开实现

1. 按骨架顺序分块写入，不一次性整文件灌入。
2. 优先顺序通常为：
   - 入口/路由
   - 公共库
   - 业务域实现
   - 收尾与集成
3. 分块尽量保持“每块可独立验证”。

### 阶段 4：每段即验

每完成一块，至少做一项验证：

- 语法检查（如 `bash -n` / `tsc --noEmit` / `python -m py_compile`）
- 最小 smoke test
- 局部测试
- 关键路径命令 help / dry-run 验证

**没有验证，不得宣称该块已完成。**

### 阶段 5：工具降级与容错

若出现大文件写入/编辑失败，执行以下降级：

1. `Write` 失败 ≥3 次 → 改用 `apply_patch`
2. `apply_patch` 仍困难 → 再拆小块
3. 单块过大 → 先写骨架，再逐段补函数体
4. 禁止在失败后继续尝试一次性整文件重写

### 阶段 6：交付收尾

1. 汇总实际落地文件。
2. 汇总验证结果。
3. 标注未完成项/风险点。
4. 若该模式产生了通用经验，补充到 skill 文档或 reference。

## 评审检查清单

评审时（无论文档还是代码）关注以下维度：

| 维度 | 检查要点 |
|------|----------|
| 结构完整性 | 章节是否覆盖命题所有关键面？是否有明显缺失？ |
| 逻辑连贯性 | 章节顺序是否合理？前后是否有断裂或重复？ |
| 抽象-具象平衡 | 是否既有框架又有证据？是否有空洞的泛论？ |
| 读者适配 | 对目标读者是否合适？术语/深度/前置知识假设？ |
| 体量合理性 | 各章比例是否失衡？是否有过长或过短的章节？ |
| 可操作性 | 读者看完能否动手？是否缺少模板/示例/步骤？ |
| 验证闭环 | 每个实现块是否都有最小验证？ |
| 分块质量 | 是否真的分块，而不是伪分块后一次性灌入？ |

## 常见错误

| 错误 | 正确做法 |
|------|----------|
| 大纲只列标题不写摘要 | 每章必须有 1-2 句说明"写什么" |
| 用户说"差不多"就当确认 | 必须得到明确的"可以/确认"才算通过 |
| 写到一半大幅改结构不告知 | 结构变更必须先说明理由并获确认 |
| 全文一次性输出不分阶段 | 逐章撰写，标记进度 |
| 评审意见只改一部分 | 逐条处理，明确标注每条的处置结果 |
| 大代码文件一次性整块写入 | 先骨架，再分块 patch/编辑 |
| Write 失败后继续硬重试 | 3 次后切换方案 |
| 分块实现后不验证 | 每块至少做一次最小验证 |

## 与其他 Skill 的关系

- **brainstorming**：如果文档的命题/方向尚未明确，先用 brainstorming 探索需求，再进入本 skill 的大纲阶段。
- **requesting-code-review**：正文评审阶段可复用其评审调度模式。
- 本 skill 现在同时覆盖：**长文写作** 与 **大文件/多文件代码实现**。
- 当任务主要难点是“体量太大、不能一次性产出”时，优先使用本 skill。
